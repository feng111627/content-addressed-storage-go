# 本地去中心化内容寻址存储（Go）

用**本地磁盘 + 内存**模拟多个去中心化存储节点，实现内容的切分、内容寻址、
多副本写入与带完整性校验的取回。在**节点故障**与**数据静默损坏/篡改**等情况下，
系统要么给出与原文逐字节一致且可验证的内容，要么返回**可区分原因**的错误，
绝不返回错误内容。

## 目录结构

```
internal/cas/    核心原语：内容标识、定长分片、可寻址的分片清单、可区分错误
  chunk.go       内容标识与分片/重组
  manifest.go    分片清单（自身可寻址、确定性序列化、结构校验）
  errors.go      ErrChunkMismatch / ErrMissingChunk / ErrInsufficientNodes ...
internal/node/   存储节点抽象与实现（内存节点 + 磁盘持久化节点、故障/损坏注入）
internal/store/  多节点协调：多副本写入、并发去重、校验取回、副本放置
cmd/demo/        可运行的端到端演示（5 个业务场景）
```

## 一、内容寻址规则

- 标识算法：`SHA-256`，形如 `sha256-` + 64 个小写十六进制字符（共 71 字符）。
- **相同内容 → 相同标识；任意一位变化 → 标识必然不同**（抗碰撞由 SHA-256 保证）。
- 三层对象都按内容寻址：
  1. **分片（chunk）**：`chunkID = sha256(chunkBytes)`。
  2. **分片清单（manifest）**：记录整体内容标识、分片大小、原始长度，以及按序号排列的
     `(分片ID, 长度, 序号)` 引用；清单用**确定性紧凑 JSON**（固定字段顺序、无多余空白）
     序列化后再做 SHA-256，即 `manifestID = sha256(canonicalJSON(manifest))`。
     规范化表示保证跨进程、跨机器得到同一清单标识。
  3. **整体内容（content）**：`contentID = sha256(重组后的完整字节)`。
- 节点上的存储键分命名空间，互不冲突：
  - 分片：`cas/chunk/<chunkID>`
  - 清单：`cas/manifest/<manifestID>`
  - 索引：`cas/index/<contentID>`，其值为对应的 `manifestID`
- **空内容语义确定**：`nil` 与 `[]byte{}` 等价；切分为 0 个分片；
  整体标识固定为
  `sha256-e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
  （即 SHA-256 空串）；仍会持久化一份清单，取回确定得到 0 字节。
- **超大内容语义确定**：按固定 `ChunkSize`（默认 16 KiB，可配，上限 64 MiB）切分，
  除最后一片外每片等长，最后一片 ≤ ChunkSize；分片数 `ceil(len/size)` 确定。
  提供 `SplitReader` 流式切分；重组后用整体哈希做最终校验。

## 二、副本策略

- 副本因子 `Replication`（默认 3）：**每个分片、清单都必须在该数量的不同节点上
  写成功且读回校验一致，才算成功**；节点不可用、写入错误、读回不一致都不计入成功。
- **副本放置**：对每个对象键（分片/清单/索引）与节点 ID 拼接后做 SHA-256 排序，
  确定性地选出节点序列——同一片的放置顺序稳定可复现，不同分片均匀打散到不同节点，
  避免所有分片集中在同一批节点。
- **重试与取舍**：首选 `Replication` 个位置之外，最多再尝试 `MaxRetries` 个健康节点；
  不健康节点直接跳过且不消耗重试预算。
- **副本不足是显式失败**：凑不齐副本数时返回 `*cas.ReplicationError`，
  `errors.Is(err, cas.ErrInsufficientNodes)` 成立，错误中带有
  `ChunkID / Required / Achieved / 每个节点的失败原因`，调用方可精确区分
  “节点不够 / 写入报错 / 读回不一致”。失败的整体写入不会落下可被取回的半成品
  （没有成功的清单与索引）。
- **并发写同一内容去重（单飞）**：以 contentID 为键，同一时刻只有一个实际写入流程，
  其余并发调用等待并复用同一结果。配合“所有对象键都按内容寻址”的天然幂等，
  并发写同一内容不会产生重复分片或损坏的副本记录；重复写入已存在内容走幂等快速路径。
- 索引 `contentID -> manifestID` 会尽量扩散到所有健康节点，因此只要还有任一节点存活，
  就能定位到清单；清单本身按副本因子保存多份。

## 三、校验与损坏恢复策略

取回时进行**多级校验**，任何一级不过都不会把数据返回给调用方：

1. **清单校验**：重算清单字节的 SHA-256，必须等于寻址用的 manifestID；
   并校验内部结构（序号连续、长度与 ChunkSize 一致、长度之和等于声明长度、ID 格式合法）。
   损坏的清单副本会被跳过，自动尝试其它副本。
2. **逐分片校验**：对每个分片副本检查长度，并重算 `sha256(分片数据) == chunkID`。
   - 摘要不符（被篡改/位腐烂）或长度异常 → 记为一条 `CorruptionError`（含节点 ID、分片 ID），
     **识别并跳过该坏副本**，继续尝试其它节点；
   - 只要还有任意一份完好副本，就用它重组，内容可被完整恢复。
3. **整体校验**：用 `Join` 重组（再次逐片校验 + 校验序号连续），核对总长度等于清单声明，
   最后重算 `sha256(整体) == contentID`。全部通过才返回。
4. **无法修复时明确报错**：某分片在所有节点上都没有完好副本时返回
   `cas.ErrMissingChunk`（错误信息含坏副本数、缺失节点数）；清单/内容不存在分别返回
   `ErrManifestNotFound` / `ErrContentNotFound`。
5. 节点写入采用**临时文件 + 原子 rename**，避免崩溃留下半截对象；磁盘对象文件名用
   十六进制编码，键中含 `/` 等字符也能无损往返。

## 四、本地验证方法

要求 Go 1.25+（见 `go.mod`）。

```bash
# 1) 一键跑全部单元测试
go test ./...

# 2) 详细日志：可直接看出覆盖了哪些业务、每个业务有哪些用例及通过情况
go test -count=1 ./... -v

# 3) 竞态检测（并发去重路径建议带上）
go test -race -count=1 ./...

# 4) 运行端到端演示（临时目录落盘，跑完自动清理）
go run ./cmd/demo
```

### 单元测试覆盖的业务

| 业务 | 覆盖要点 |
| --- | --- |
| 内容标识稳定性 | 相同内容同标识、逐位变化标识必变、算法/格式正确、空内容确定 |
| 分片与重组 | 序号/长度/标识正确、空内容、稳定性、非法大小、损坏拒绝、缺序号拒绝、流式等价 |
| 分片清单可寻址 | 整体标识/长度、清单自身标识稳定、序列化确定、篡改/坏片/结构异常被拒、空内容清单 |
| 内存/磁盘节点 | 读写往返、数据隔离、ErrNotFound、删除幂等、落盘与重启加载、损坏注入 |
| 多副本写入 | 每片恰为 N 个不同节点、正常取回一致、按清单取回、重复写入幂等不增对象 |
| 故障导致副本不足 | 健康节点不足→`ErrInsufficientNodes`(含 required/achieved)、自动换节点重试、失败不留半成品 |
| 坏分片检测与恢复 | 坏 1/坏 2 份自动跳过坏副本恢复、全坏→`ErrMissingChunk` 不返回坏内容、长度异常判定 |
| 取回时节点故障 | 部分节点下线仍取回、全部下线→可区分 NotFound |
| 并发写入去重 | 16 协程同内容单飞（物理写入仅一次规模）、不同内容并发互不干扰 |
| 空内容与超大内容 | 空内容确定语义、256KiB/64 分片写入取回整体校验 |
| 磁盘持久化与重启 | 分片/清单/索引落盘后重建 Store 完整取回 |
| 整体内容校验 | 尾分片多副本损坏仍靠好副本恢复并通过整体哈希 |

### 演示程序的 5 个场景

1. 切分 + 内容标识 + 3 副本写入，打印每个分片的副本节点；
2. 一个节点故障，仍取回并整体校验通过；
3. 在某节点上篡改分片，系统识别坏副本、跳过并从好副本恢复；
4. 破坏某分片的全部副本，得到可区分的 `ErrMissingChunk`；
5. 令所有节点下线后写入，得到带 `required/achieved/失败明细` 的
   `ReplicationError`（`ErrInsufficientNodes`）。

## 关键错误判别（errors.Is）

| 哨兵错误 | 触发情形 |
| --- | --- |
| `cas.ErrChunkMismatch` | 分片数据重算哈希与其标识不一致（损坏/篡改） |
| `cas.ErrMissingChunk` | 某分片在所有可用节点上都没有完好副本 |
| `cas.ErrManifestMismatch` | 清单自身哈希或内部结构校验失败 |
| `cas.ErrContentMismatch` | 重组后的整体哈希与 contentID 不一致 |
| `cas.ErrInsufficientNodes` | 健康节点无法满足副本因子（由 `*ReplicationError` 包装，含明细） |
| `cas.ErrManifestNotFound` / `cas.ErrContentNotFound` | 清单 / 内容在所有健康节点上均不存在 |
